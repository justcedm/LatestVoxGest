1. Executive Summary
VoxGest is an offline Android edge-computing accessibility prototype designed to assist communication 
between sign language users and hearing or non-signing individuals. The system uses camera-based 
landmark tracking and trained machine learning models to recognize selected signs, convert accepted 
outputs into text and speech, and support a reverse communication path through speech-to-text and 
lightweight avatar or fingerspelling feedback.
The most important correction for the paper is that VoxGest is no longer only a CNN-based static 
alphabet recognizer. The current system is a layered recognition and communication tool. It includes 
static alphabet/control recognition, selected dynamic word recognition, a NOTHING negative class, 
token-based sentence composition, Android/TFLite deployment planning, and avatar playback 
downstream of confirmed accepted tokens.

3. Why the System Took This Direction
3.1 Why the Original CNN-Only Direction Had to Change
The project started with CNN-based image recognition because CNNs are familiar and effective for 
image classification tasks. The first idea was to let the model learn hand shapes from static ASL alphabet 
images. This made sense for a beginning prototype, but live camera testing exposed a domain gap: 
clean dataset images are different from webcam and phone camera conditions.
The CNN approach became sensitive to background, lighting, camera angle, hand distance, cropping, 
and signer position. Because the project needs reliable live recognition, the team moved toward 
landmark-based recognition. Landmarks represent the hand and body as numerical points, allowing the 
model to focus on geometry rather than the entire image.
3.2 Why Static Signs Use 63 Features
Each hand has 21 landmarks, and each landmark has x, y, and z coordinates. Therefore, the static 
feature vector has 21 x 3 = 63 features. This is used for A-Z, del, space, and nothing. The static model 
normalizes the hand around the wrist and scales it by hand size, making the model less dependent on 
the exact camera position.
3.3 Why Dynamic Words Use 30 x 162
Dynamic signs need motion over time. The dynamic word model uses 30 frames per decision window. 
Each frame contains 99 pose features and 63 dominant-hand features, for a total of 162 features per 
frame. This gives the model both motion information and body-relative location. Body-relative location is 
important because some signs depend on whether the hand is near the face, chest, or another body 
region.
3.4 Why NOTHING Is Required
A softmax word classifier will always choose some word if it is forced to classify every input. This can 
produce false outputs when the user is idle or only moving casually. NOTHING teaches the model what 
no valid word looks like. This makes the system safer and more reliable because idle hands, open hands, 
aborted signs, transitions, and partial gestures can be rejected rather than spoken or displayed.
3.5 Why the One-Hand/Dominant-Hand Policy Exists
The current goal is not full multi-hand ASL fluency. The goal is reliable one-hand accessibility for a 
mobile communication utility. A dominant-hand policy supports users who sign with one hand by

 The communication problem is real and affects daily interaction, public service, healthcare, school, 
and employment contexts.
 VoxGest is positioned as an assistive communication prototype, not a replacement for interpreters.
 The system is bidirectional: sign-to-text/speech and speech-to-text/avatar response.
 The current scope is controlled: static alphabet, 10 dynamic words, NOTHING, token composer,

 The limitations are honest: no full ASL grammar, no unrestricted vocabulary, phrase recognition 
currently disabled, avatar is lightweight.

 MediaPipe and landmark literature supports the shift from raw images to hand/body coordinates.
 LSTM, TCN, and WLASL literature supports dynamic word recognition.
 Edge computing and TensorFlow Lite literature supports offline Android deployment.
 Accessibility and sign language technology literature supports bidirectional communication needs.
 ISO/IEC 25010 literature supports the evaluation categories.

 Static alphabet/control recognition exists using landmark features.
 Dynamic word recognition exists for the demo10 vocabulary plus NOTHING.
 The project identified and documented the floating-hand problem and fixed it using pose + hand

10. Current Limitations to State Honestly
 The system cannot yet translate full ASL grammar.
 The system does not recognize an unrestricted vocabulary.
 Phrase-level recognition is not part of the current default demo because recognition hardening is the 
priority.
 Dynamic word validation is demo-ready but not production-ready; weak words still need repair data 
and live testing.
 Android real-time CameraX + MediaPipe + TFLite integration is still being prepared.
 The avatar is a lightweight prototype and not a complete ASL avatar.
 Environmental factors such as lighting, camera angle, distance, and hand visibility can still affect 
recognition.

13. Final Project Positioning
The best way to present VoxGest is as a capstone-stage assistive communication prototype. It is not yet 
a full ASL translator, but it is a meaningful and technically defensible system because it combines live 
camera input, landmark extraction, static recognition, dynamic recognition, negative-class rejection, token 
composition, speech output, speech-to-text response, and avatar/fingerspelling feedback into a single 
offline Android accessibility direction.
The paper should always describe what the system actually does now, not what the earliest proposal 
planned and not what the future expansion may eventually become. The strongest defense position is 
honesty plus clear engineering logic: VoxGest started with CNN, found live limitations, moved to 
landmarks and temporal models, added NOTHING and gates for reliability, froze expansion for 
hardening, and prepared Android/TFLite integration for local use.
