1. The Whole Project in One Very Simple Picture
Imagine one phone placed between two people:
 The Deaf/signing user signs in front of the phone camera.
 The phone watches the hand and body using landmark dots.
 The AI chooses only stable, accepted signs.
 The app writes the accepted message as text.
 The app can speak the confirmed text out loud.
 The hearing person can speak back.
 The app turns the spoken reply into text and can show a simple avatar or fingerspelling response.
Simple meaning:
VoxGest tries to become a small communication bridge. It does not replace a human interpreter. It helps 
with controlled, common, simple communication when no interpreter is around.
Camera The eyes of the system. It sees the signer.
MediaPipe The dot maker. It puts points on the hand and body.
Features The numbers that describe where the dots are.
Model The trained guesser. It learned patterns from examples.
Gates The security guard. It blocks weak or fake predictions.
NOTHING The quiet label. It teaches the model: if no real sign is 
happening, say nothing.
Token Composer The sentence builder. It only uses accepted signs to build 
text.
Avatar The simple visual helper. It shows known words as small 
animations or fingerspells unknown words.
2. What VoxGest Is Right Now
Current honest description:
VoxGest is an offline Android edge-computing accessibility prototype. It recognizes controlled hand 
gestures, turns accepted signs into text/speech, and supports spoken replies through text and lightweight 
avatar/fingerspelling display.
Static Signs A-Z, del, space, nothing.
Dynamic Words YES, NO, PLEASE, WATER, HELLO, HELP, STOP, 
DOCTOR, NAME, THANKYOU.
Negative Class NOTHING. It means no valid dynamic word should be 
shown, spoken, or animated.
Current Focus Recognition Hardening v1: make the current letters, 10 
words, and NOTHING reliable before adding more 
vocabulary.
Phrase Intents Created as an advanced path, but currently off by default. 
Phrase expansion is frozen while basic recognition is 
hardened.
Android Goal Android prototype with CameraX, MediaPipe/Holistic 
landmarks, TensorFlow Lite models, token composer, and 
avatar playback.
Current limitation in simple words:
 It does not understand all ASL grammar.
 It does not know unlimited signs.
 It should not promise full sentence translation yet.
 It is demo-ready/prototype-ready, not production-ready.

3. The Logic Path: Why the System Became This Way
The project path is not random. It follows this logic:
1. Problem: Deaf/signing users and hearing/non-signing people struggle to communicate without an 
interpreter.
2. Need: A phone-based tool is more available than a human interpreter in daily situations.
3. First idea: Use CNN because CNNs are common for image recognition.
4. Real problem: Webcam conditions made raw image recognition weak and unstable.
5. Better idea: Use landmarks, because dots on the hand/body ignore much of the background and 
lighting.
6. Static signs: Use 63 hand features because one hand has 21 points and each point has x, y, z.
7. Dynamic signs: Use 30 frames because moving signs need time, not just one picture.
8. Body signs: Add pose features because some signs depend on where the hand is near the 
face/chest/body.
9. False words: Add NOTHING and gates because the model must learn when to stay silent.
10. Sentence output: Use token composer so only accepted predictions become text.
11. Bidirectional use: Add speech-to-text and avatar/fingerspelling because communication needs both 
directions.
12. Current freeze: Stop adding phrases/words until the current recognition set becomes stable.

Decision 6: Use MediaPipe Landmarks
Super simple idea: Instead of looking at the whole photo, the system follows important dots.
WHAT Convert hands/body into numerical landmark dots.
WHY Dots are more stable than raw images because they focus 
on hand/body geometry instead of the whole room.

HOW Use MediaPipe Hands or Holistic to extract x, y, z 
coordinates from detected hand and pose landmarks.
RELATION Landmarks are the bridge between camera images and

Decision 7: Use 63 Features for Static Alphabet
Super simple idea: One hand has 21 dots. Each dot has x, y, z. 21 times 3 equals 63.
WHAT Represent one hand using 21 landmarks multiplied by 3 
coordinates.
WHY Static letters mainly need hand shape, so hand-only 
landmarks are enough and efficient.
WHERE Static alphabet model, Android static runtime, paper 
methodology.
WHEN April 8-10, 2026 and continued in current system.
HOW Extract 21 hand points, subtract the wrist, scale by hand 
size, then feed 63 numbers into the static model.
RELATION This supports A-Z, del, space, and nothing recognition.
Decision 8: Use Landmark-Only Static Classifier
Super simple idea: The model judges hand shape by measuring dots, not by staring at the room.
WHAT Use a dense model/classifier on landmark numbers instead 
of relying on cropped images.
WHY It reduces background, lighting, skin tone, and camera 
quality problems.
WHERE Static recognition pipeline, model training, paper Chapter 3.
WHEN April 8-10, 2026 after hybrid failed live.
HOW Train the model using normalized 63-feature hand vectors 
for alphabet/control signs.

WHAT Expand the system from sign-to-speech only into two-way

WHY A real conversation needs both people to reply. If only the

Decision 10: Add Dynamic Word Recognition
Super simple idea: Letters are slow bricks. Words are bigger blocks.
WHAT Recognize selected moving words instead of only static 
letters.
WHY Spelling everything letter by letter is slow. Common words 
make communication faster.
WHERE Dynamic ML pipeline, live recognizer, Android runtime.
WHEN After static recognition foundation; expanded through April 
22-29 and hardening on May 10.
HOW Use 30-frame sequences and train LSTM/TCN models on 
selected words.
RELATION Dynamic words add practical usefulness while keeping

Decision 11: Use 30 Frames for Word Motion
Super simple idea: A wave needs time. One frozen picture cannot show the wave.
WHAT Represent a word as a short video sequence of 30 frames.
WHY A moving sign cannot be understood from one picture. The 
model needs before, during, and after motion.
WHERE LSTM/TCN word model, feature extractor, Android dynamic 
contract.
WHEN Established during LSTM word pipeline development.
HOW Collect/convert each sign attempt into a 30-frame x feature-
size array.
RELATION This lets the model learn motion order, not just hand shape.
Decision 12: Use 162 Features for Dynamic Words
Super simple idea: The model now knows if the hand is near the mouth, chin, chest, or body.
WHAT Use 99 pose features plus 63 hand features per frame.
WHY Some signs depend on where the hand is relative to the 
face/chest/body, not only hand shape.
WHERE Dynamic word model and Android runtime contract.
WHEN Major upgrade on April 24, 2026.
HOW Use 33 pose landmarks x 3 = 99 plus 21 hand landmarks x 
3 = 63, giving 162 numbers per frame.
RELATION This fixed the floating-hand problem by adding body location 
context.

Decision 13: Fix the Floating-Hand Problem
Super simple idea: A hand near the mouth and a hand near the chest should not look the same to the AI.
WHAT Stop treating the hand as if it floats in empty space.
WHY Hand-only normalization removed body location, so signs 
near different body parts could look confusingly similar.
WHERE Dynamic feature engineering and methodology explanation.
WHEN April 24, 2026.
HOW Switch to MediaPipe Holistic and anchor pose/hand data to 
the nose point for body-relative coordinates.
RELATION This explains why dynamic recognition needed pose 
features, not just hand features.
Decision 14: Use LSTM and TCN for Motion
Super simple idea: These models read motion like reading a short flipbook.
WHAT Use sequence models for dynamic signs.
WHY Moving signs are time-based. LSTM learns order over time; 
TCN can learn motion patterns through temporal convolution 
and may be faster.
WHERE Word model development and comparison.
WHEN During dynamic recognition work and current hardening 
sprint.
HOW Train LSTM/TCN on 30 x 162 sequences and compare 
validation plus live behavior.
RELATION This keeps the project flexible: choose the model that 
behaves better live, not only on paper.
Decision 15: Add NOTHING as a Negative Class
Super simple idea: Sometimes the correct answer is: do not say anything.
WHAT Teach the model a no-output class for idle, partial, transition, 
or non-sign movement.
WHY Without NOTHING, the model is tempted to force every 
motion into a real word.
WHERE Dynamic model, token composer, avatar rules, testing 
protocol.
WHEN Added during word-recognition fixing and active in 
Recognition Hardening v1.
HOW Record open hands, idle hands, aborted signs, hand 
entering/leaving frame, and partial signs as NOTHING.
RELATION NOTHING protects the system from embarrassing false 
words.
Decision 16: Use Gates Before Accepting Words
Super simple idea: The gate is a security guard. It asks: Are you sure this is a real sign?
WHAT Check confidence, margin, motion, wrist path, and hand 
presence before accepting a prediction.
WHY AI guesses can be unstable. Gates stop weak guesses from 
becoming real output.
WHERE Post-processing, live recognizer, Android runtime.
WHEN Added during April 22 fixes and later hardening.
HOW Only allow a word if it passes threshold rules and remains 
stable long enough.
RELATION Gates protect the token composer, speech output, and 
avatar from raw unstable predictions.

Super simple idea: Do not let the AI switch hands randomly while learning.
WHAT Let the system focus on one configured signing hand: right, 
left, or auto.
WHY The same sign can look different depending on hand. 
Controlled recording needs consistency. One-hand 
recognition also supports users with limited mobility.
WHERE Recording scripts, dynamic feature extraction, Android 
handoff.
WHEN Clarified on April 28-29, 2026.
HOW Use VOXGEST_DOMINANT_HAND and 
VOXGEST_SINGLE_HAND_POSE to keep the selected 
hand/arm and mask unrelated body parts.
RELATION This connects accessibility, data quality, and live reliability.
Decision 18: Fix Mirrored Webcam Hand Labels
Super simple idea: A mirror makes left look right. The code must remember the real hand.
WHAT Correct left/right hand meaning when webcam frames are 
mirrored.
WHY A selfie camera can flip the image, so MediaPipe labels may 
appear opposite from the user physical hand.
WHERE Python webcam scripts and Android camera behavior.
WHEN April 29, 2026 knowledge update.
HOW Map physical left/right to the correct MediaPipe label when 
mirrored_input is true.
RELATION This prevents wrong-hand data and improves controlled 
recording.

8. Defense-Friendly Explanation
Use this when someone asks what VoxGest really is:
VoxGest is a capstone-stage offline Android accessibility prototype. It recognizes controlled one-hand signs 
using camera landmarks, builds text only from accepted predictions, speaks confirmed signed text, and 
supports spoken replies through text and lightweight avatar or fingerspelling feedback.
Use this when someone asks if it fully translates ASL:

--- PAGE 12 ---
No. The current system does not claim full ASL grammar translation. It supports static alphabet signs, 
selected dynamic words, and a controlled token-based sentence composer. Phrase-intent recognition exists 
as a future/optional path, but it is disabled during Recognition Hardening v1.
Use this when someone asks why the system changed from CNN:
The project started with CNN because CNN is a normal image-recognition approach. Live webcam testing 
showed that raw images were sensitive to background, lighting, camera angle, and cropping. The system 
moved to landmarks because landmark numbers focus on hand/body geometry and are easier to match 
between Python and Android.
Use this when someone asks why NOTHING is important:
NOTHING prevents the AI from speaking random words when the user is idle, moving naturally, starting a 
sign, stopping a sign, or doing a non-sign motion. It is a safety and reliability class, not a real spoken word.
Use this when someone asks why one hand:
One-hand recognition supports accessibility. Some users may sign with one hand because of preference, 
injury, limb difference, stroke, or physical limitation. It also keeps the current model simpler and more 
reliable for mobile real-time use.

11. Common Misunderstandings to Avoid
Wrong VoxGest fully translates ASL sentences.
Correct VoxGest recognizes controlled letters and selected words, 
then builds sentence text from accepted tokens. Phrase-
intent is future/optional and disabled during hardening.
Wrong CNN is the final main model.
Correct CNN was an early approach. Current static recognition uses 
landmarks; dynamic words use temporal landmark 
sequences.
Wrong NOTHING is a word shown to the user.
Correct NOTHING is a no-output negative class. It should never be 
displayed, spoken, or animated.
Wrong More words means better progress.
Correct Stable current words are better than many weak words. Add 
vocabulary only after hardening.
Wrong Validation accuracy alone proves success.
Correct Live testing matters because camera behavior, hand 
selection, lighting, and motion timing affect real use.

Final simple conclusion:
VoxGest started as an image-based sign recognizer, learned from real webcam problems, moved to 
landmark-based recognition, added motion models for words, added NOTHING and gates for safety, added 
token composer for controlled sentence output, and prepared Android/avatar integration for bidirectional 
communication. The correct defense story is not “we kept changing because we were lost.” The correct story 
is “we improved the architecture whenever real testing revealed a weakness.”
